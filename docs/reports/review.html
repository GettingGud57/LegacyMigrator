Can we trust the PASS?

I reviewed the pipeline looking for ways it could say "the translation matches" when it doesn't, or let the AI see the answer. I found real ones, proved each with a small run, and turned them into tests you can tick off.

One-screen summary

22failing tests = your to-do list
37passing tests that lock in what works

The core idea holds up. Comparing whole rows as a multiset (rows can be in any order, but every row must appear the same number of times) is the right design. Hundreds of random tables with a random known change all got caught. The Sale translation also matches the T-SQL on every edge case I tried for the lookups, NULLs and the delete-then-reinsert.

The risks are around the edges of that idea: which tables get compared, what gets compared (values but not types), what happens to "ignored" columns, stale files, and the fact that the generated code can read the answer key. Two harness bugs will also make honest translations fail on your Mac but not on a UTC machine, or crash on holdout data.

What I added

Nothing in migrator/ or jobs_pyspark/ changed. Everything new is in tests/, plus pytest.ini and this report.

A fake SQL Server that drives the real run_legacy code

tests/snapshot_builder.py has a FakeCursor that pretends to be a pyodbc cursor. It knows each table's declared SQL type (copied from the WWI warehouse) and a handful of hand-made rows. The tests hand it to the real run_legacy.snapshot(), so the Parquet files come out exactly how your Mac would write them, quirks included.

Why this matters: when you fix finding 8 in run_legacy.py, the end-to-end Spark tests built on top of it start passing on their own. If the builder wrote Parquet itself, they'd keep testing the old behaviour forever.

Tests as a to-do list

Every finding I could reproduce has a test marked @pytest.mark.bug that fails today and should pass once the bug is fixed. Next to them are lock-in tests for what already works, so a fix can't quietly break something else. tests/README.md maps each failing test to its finding and says what order to fix things in.

python -m pytest -m bug           # the to-do list: 22 failing
python -m pytest -m "not bug"     # what works today: 37 passing

Property tests for the checker

tests/test_diff_properties.py uses Hypothesis to make hundreds of random little tables (ints, text with accents, 2-place decimals, dates, year-9999 timestamps, booleans, NULLs). For each one it makes a change that definitely matters: edit a cell, drop a row, duplicate a row, swap two values between rows. Every single one got caught. Shuffling rows never caused a FAIL. That's good evidence the multiset idea at the heart of diff.py is right.

End-to-end runs of the real Sale translation

tests/test_run_spark.py runs python migrator/run_spark.py sale jobs_pyspark/sale.py exactly like you do, on a 2-line staging table. I worked out the expected results by hand from the T-SQL: staging gets City Key 5, Customer Key 7, Stock Item Keys 8 and 9, Salesperson Key 4; invoice 100's old line disappears from Fact.Sale and two new lines appear with Lineage Key 2; lineage row 2 is closed; the Sale cutoff moves to 2016-06-06 12:31:17. All four checks pass.

Before and after: where the trust can leak

The findings

In order of how much damage they do to the claim "the old system's real output decides". Each has a tiny example, why a judge would care, a hint toward the fix (not the fix), and its test.

Wrong PASS

false PASS1. diff.py only compares Integration.Sale_Staging

The Sale job changes four tables: Sale_Staging, Fact.Sale, Lineage and ETL Cutoff. python migrator/diff.py only ever looks at Sale_Staging. A translation that writes garbage into Fact.Sale still prints PASS. If spark/Fact.Sale.parquet is missing entirely, nothing notices.

Example
Fact.Sale in after/ has Quantity 3 and 1; in spark/ both are 999. Output of python migrator/diff.py sale: 
=== Sale_Staging: after (legacy) vs spark (translation) ===
PASS
  identical-twin check: 0 rows in A and 0 in B have no identical twin (2 columns compared)
Should be: FAIL, naming Fact.Sale.
Why it matters
The demo story is "every table the old job wrote matches". Right now it's one table out of four, and the one with the fewest moving parts.
Fix hint
Loop over every file in after/. A file missing from spark/ is a FAIL, and so is an extra one. Exit with a non-zero code on any FAIL, so a script (or loop.py) can't miss it. check.py on test-bench does exactly this; worth reading.
Test
test_diff.py::TestFinding1_EveryTableIsCompared (2 tests)

false PASS2. Column types are never compared

diff.load() turns every cell into a plain Python value. Python then says these are equal: Decimal("1.10") == Decimal("1.100000"), 3 == 3.0, True == 1. So a translation that changes a column's type passes, as long as the values look the same.

Example
Legacy Unit Price is decimal(18,2) holding 1.10. Spark writes decimal(38,6) holding 1.100000 (Spark's decimal arithmetic widens like this all the time). Today: PASS. Should be: FAIL, "Unit Price: decimal(18,2) vs decimal(38,6)". Same for decimal to double (2.5), int to double, int to bigint, bit to int. All five reproduced.
Why it matters
A technical judge will ask "what if the types drift?" The downstream table is decimal(18,2); a double column is a different table even if today's numbers happen to look the same. Also, the type is the thing that makes the next month's numbers round differently.
Related
When a type does differ in a way Python notices, the message is confusing. A Spark "timestamp with timezone" next to SQL's plain datetime2 shows up as datetime(2016, 6, 6, 12, 31, 17) -> datetime(2016, 6, 6, 12, 31, 17, tzinfo=utc) on every row. test-bench's first Movement translation failed in exactly this way: 27 rows that "differ" only in type.
Fix hint
Read both schemas with pq.read_schema() and compare them field by field before comparing rows. Report type differences on their own line. Do finding 8 first, or the legacy types you compare against are guesses.
Test
test_diff.py::TestFinding2_TypesAreCompared (5 cases)

false PASS3. Ignoring a column means not looking at it at all

Some columns can never match between two runs: Data Load Completed is set by SYSDATETIME(), and Sale Key comes from an identity counter (finding 10). They'll have to be ignored. But ignore_cols removes them from the comparison completely, so a translation that forgets the UPDATE also passes.

Example
Legacy: Data Load Completed = 2026-11-04 21:00:01. Spark: NULL (the translation never closed the lineage row). With ignore_cols=["Data Load Completed"]: PASS. Should be: FAIL. But a different time must still PASS.
Why it matters
The ignore list is exactly where a skeptical judge will poke. "You ignored the column the bug was in" is a bad answer to have to give.
Fix hint
Instead of dropping the column, replace each value with "has a value" or NULL before comparing, so filled-in vs empty still counts. test-bench's check.py calls this mask(), and also checks that rows the legacy job didn't touch come out of Spark identical in every column, ignored ones included.
Test
test_diff.py::TestFinding3_IgnoredColumnsStillGetChecked (one fails now; the other must keep passing)

false PASS4. A crashed run leaves the previous run's output behind

run_spark.py only clears spark/ after the job has run. If the job crashes first, it exits and the old files stay. The next diff.py grades the old translation's output.

Example
Run the noop job (writes all 8 files). Run a new translation that raises an error: exit code 1, but all 8 old files are still in spark/. Run diff.py: it compares them and prints PASS.
Why it matters
This bites hardest in loop.py: retry 3 crashes, the loop reads the folder, and reports retry 2's verdict as retry 3's. In a live demo nobody would spot it.
Fix hint
Clear spark/ at the very start, before anything can fail. Write a small "done" file last (test-bench writes run.json) that names the job file, and have the checker refuse a folder without it.
Test
test_run_spark.py::test_finding4_failed_run_leaves_no_old_output

false PASS5. Two empty tables always pass

reconcile() learns the column names from the first row. An empty table has no first row, so it has no columns as far as the checker knows.

Example
Legacy: empty table with column City Key int. Spark: empty table with column Wrong Column string. Today: PASS, "0 columns compared". Should be: FAIL.
Why it matters
Small today, but holdout data should include a quiet day (empty staging), and some jobs only touch a table in rare cases. "0 columns compared" next to PASS also looks bad on screen.
Fix hint
Take column names from the file's schema, not from rows[0]. The same schema read as finding 2.
Test
test_diff.py::TestFinding5_EmptyTables

The AI near the answer

integrity6. The generated job can copy the answer key

run_spark.py imports the AI's file and runs it as ordinary Python, from the repo folder, with full access to your Mac. The contract says "no reading files", but nothing enforces it.

Example
This "translation" translates nothing: 
def run(spark, tables):
    out = {}
    for path in glob.glob("snapshots/sale/after/*.parquet"):
        out[os.path.basename(path)[:-8]] = spark.read.parquet(path)
    return out
I gave after/ a Quantity of 42 that no honest translation could guess. Result: run_spark exit 0, verdict PASS.
Why it matters
This is the one that breaks the pitch. "The AI never grades its own work" needs "and it can't peek at the answers" next to it. With a retry loop feeding failures back, a model optimising for PASS could land on this. It could also overwrite after/.
Fix hint
Run the job in a separate process whose working folder is a temp folder holding only a copy of before/, so relative paths can't reach after/. Store a hash of each after/ file in meta.json and check it before grading, so tampering is caught. An absolute path would still get out; for that, run Spark in a Docker container with only the input folder mounted and no network. The relative-path test is the bar for now.
Test
test_run_spark.py::test_finding6_job_cannot_copy_the_answer_key

integrity7. claude -p keeps its file and shell tools while translating

Good news first: translate.py already runs claude in an empty temp folder (the brief said the repo folder; that changed in commit 3292358). The prompt holds table layouts and the SQL, never rows. But claude -p still has Read, Bash and the rest, and what they may touch is decided by your own ~/.claude settings. An empty working folder isn't a wall.

Example
Called today as ["claude", "-p"]. Should be ["claude", "-p", "--tools", ""]. I checked claude --help (v2.1.318): Use "" to disable all tools.
Status
The risk is plausible, not reproduced. I didn't run a real translation to see whether it would read snapshots/. The test checks the command line only.
Why it matters
Once the holdout exists, "the translator had no tools at all" is a much simpler sentence for the Responsible AI note than "it ran in a temp folder and probably didn't look".
Fix hint
Add "--tools", "" to the command. The translator only has to write text. test-bench also moved the answer keys out of the repo during its translations, which is a belt to go with these braces.
Test
test_translate.py::test_finding7_claude_gets_no_tools

Wrong FAIL (the harness, not the translation)

false FAIL8. run_legacy guesses each column's type from its values

read_table() builds each column with pa.array(values). pyarrow then guesses a type from whatever values happen to be there. The real SQL type is never used.

Example
What comes out for Fact.Sale in my tiny snapshot:
ColumnSQL typeParquet type today
Unit Pricedecimal(18,2)decimal(6,2), because the largest value is 1899.00
Tax Ratedecimal(18,3)decimal(5,3)
Quantityintint64
Staging City Key (all NULL before the job)intnull
Any column of an empty tableanythingnull
What breaks
sale.py casts new rows to Fact.Sale's (guessed) types. Stage a line priced 12,500.00, which SQL Server's decimal(18,2) takes happily, and Spark crashes: 
[NUMERIC_VALUE_OUT_OF_RANGE.WITH_SUGGESTION] 12500.00 cannot be represented as Decimal(6, 2).
Give it a day with no sales (empty staging) and it crashes differently, because every column became null, which Spark reads as int: 
Cannot resolve "(Last Modified When > __d_from)" due to data type mismatch:
... ("INT" and "TIMESTAMP_NTZ")
My first tiny fixture even crashed on 12.30 vs decimal(3,2) before I padded Fact.Sale with a big row.
Why it matters
It doesn't show on the dev month because Fact.Sale has 228k rows, so the guessed precision is wide. But the holdout is exactly where a new largest value or an empty day turns up, and the translation gets blamed for a harness bug. It also means the AI's prompt shows decimal128(6, 2) and null instead of the real types, and it's why finding 2 can't be fixed alone.
Fix hint
Build a pa.schema from the column metadata (sys.columns has precision and scale; pyodbc's cursor.description has them too) and pass it to pa.table(..., schema=...). A small mapping does it: int to pa.int32(), bigint to pa.int64(), bit to pa.bool_(), decimal(p,s) to pa.decimal128(p, s), date to pa.date32(), datetime2 to pa.timestamp("us"), nvarchar to pa.string().
Heads-up
Once 8 and 2 are both fixed, expect Integration.Sale_Staging to flip to FAIL: sale.py casts the keys to long (64-bit) but the columns are int (32-bit). That's a true finding the loop should fix. Don't hand-edit the translation.
Tests
test_run_legacy.py::TestFinding8_DeclaredTypesAreKept (5) and test_run_spark.py::TestFinding8_GuessedTypesBreakTheTranslation (2)

false FAIL9. Results depend on the laptop's timezone

sale.py reads Source System Cutoff Time into Python with .collect(), then puts it back with F.lit(). PySpark reads a plain Python datetime in the laptop's timezone. The session setting spark.sql.session.timeZone = UTC doesn't cover this.

Example
Same translation, same input, ETL Cutoff for Sale:
Machine timezoneCutoff Time written
UTC2016-06-06 12:31:17 (right)
Europe/Dublin (June is UTC+1)2016-06-06 11:31:17
America/New_York2016-06-06 16:31:17
Prediction
On your Mac (if it's set to Irish time), Integration.ETL Cutoff will FAIL by exactly one hour the first time you compare it. test-bench reports Sale passing on all 8 tables, but its bench runs in UTC, so that's consistent with this prediction rather than against it.
Why it matters
A verdict that changes with the laptop's clock setting can't be trusted either way. And it would happen on stage, in Dublin.
Fix hint
In start_spark(), before the JVM starts: os.environ["TZ"] = "UTC" then time.tzset(). I tried exactly that on a scratch copy of run_spark.py with the Mac set to Dublin: the cutoff came out right. Pinning the JVM too (-Duser.timezone=UTC in spark.driver.extraJavaOptions) is a sensible extra.
Test
test_run_spark.py::test_finding9_result_does_not_depend_on_laptop_timezone

false FAIL10. Sale Key can never match

Sale Key is an identity column: SQL Server hands each new row the next number from a counter. A rollback doesn't give numbers back, so every run_legacy.py run burns 5,224 numbers. sale.py uses "largest existing key + row number" instead, which only matches on the very first run after a restore, and even then only if SQL Server happens to insert in staging-key order.

Evidence
Not reproducible here (no SQL Server). But test-bench ran the legacy job twice on the same input on a real SQL Server and compared: Sale Key differed on all 5,224 inserted rows (243938 in run 1, 249162 in run 2). Everything else in Fact.Sale agreed. Data Load Completed differed on its 1 row. That's the proof ground rule 2 asks for before ignoring a column.
Fix hint
Mask Sale Key for new rows (finding 3's approach). Then add the checks that are still possible: new keys are unique, and none of them reuse a key from before/. Copy the "run the legacy job twice" trick into your own toolkit; it's the honest way to build any job's ignore list.
Test
None here. test-bench's migrator/probe.py is the check.

false FAIL11. datetime2 loses its last digit

plausible, not reproduced SQL Server's datetime2(7) stores times to 100 nanoseconds. Python's datetime stops at microseconds, so pyodbc drops the 7th digit. The T-SQL compares [Last Modified When] > [Valid From] at full precision; Spark compares the trimmed values. Two times 300 ns apart become equal, and a strict > can flip.

Why only plausible
I can't run SQL Server here, and WWI's validity dates look like whole seconds, so it may never happen on this data.
How to check on your Mac
SELECT COUNT(*) FROM Integration.Sale_Staging WHERE DATEPART(nanosecond, [Last Modified When]) % 1000 <> 0, and the same on each dimension's Valid From and Valid To. Zero everywhere means you can stop worrying.

Small things, no test

  • translate.py's prompt has a typo the AI reads every time: "Work out the right type froasm the SQL".
  • ask_claude has no timeout, so a hung claude hangs the loop forever. subprocess.run(..., timeout=600) fixes it.
  • When a Spark job fails, the real error is buried under a several-kilobyte JSON log line from Spark's DataFrameQueryContextLogger. Printing only the exception's first line, then "full trace below", would help a lot in a live demo.
  • translate.py reads the SQL with read_text(), so the file's byte-order mark goes into the prompt. Harmless, but encoding="utf-8-sig" (as run_legacy already uses) is tidier.
  • If the procedure fails inside run_legacy.py, before/ is new but after/ is left over from the last run. Clearing after/ first (like finding 4) avoids a mismatched pair.

Decisions I made, and why

  • Tests that fail today, on purpose. You asked for a to-do list you can tick off. A failing test is a to-do item that checks itself. The bug marker keeps them separate, so -m "not bug" stays green as a safety net while you work.
  • Drive the real run_legacy through a fake cursor instead of writing Parquet in the tests. Otherwise the end-to-end tests would freeze today's quirks in place and never notice your fix.
  • Run run_spark.py as a command, the way you do, rather than importing its functions. Slower (a Spark start per test, ~15 seconds each), but it catches what a real run catches: the working folder, environment variables, exit codes.
  • One helper to update when APIs change. Tests go through verdict_for_files() and run_spark_cli() in tests/conftest.py, so renaming something in diff.py means changing one function, not twenty tests.
  • No sale.py correctness tests beyond a smoke test. Hand-written expected values for translations are a small version of "the AI's helper grades the AI". The real answer key has to come from SQL Server, and the holdout is the sibling branch's job. I listed the cases instead.
  • Python 3.10 for every run, to match your Mac (the container had 3.13). Same PySpark (4.2.1) as test-bench pins.
  • Severity order follows the pitch, not how hard a bug is to fix. A wrong PASS ranks above a crash, because a crash is loud and a wrong PASS is silent.

What didn't work, limits, what's left

  • No SQL Server here. Findings 10 and 11, and the collation and NOT NULL rows in the sale.py table, are reasoned from the T-SQL and documented SQL Server behaviour. Finding 10 is confirmed by test-bench's real run; 11 and those two table rows are not.
  • Finding 7's real risk isn't measured. I didn't run a live translation to see whether Claude would actually read files outside its folder; the test checks the command only.
  • Finding 6's test uses a relative path. A sealed working folder fixes that test, but an absolute path would still reach after/. Fully closing it needs a container or a separate OS user.
  • The tiny fixture's column lists are trimmed for the dimension tables, and I typed the WWI column types from memory of its DDL; worth a glance against sp_help.
  • I first wrote my fixture with small Fact.Sale values, and the baseline crashed. That became finding 8's best evidence, and the fixture now carries one big row with a comment saying why.
  • Left for you: the fixes themselves, deciding whether int vs bigint should be a FAIL or a warning, and the "legacy job errored" case in the harness.

Explaining this to the judges

For the teammate. No Spark or data-warehouse knowledge needed.

What the tool does. Old company systems run "jobs" every night that move and tidy up data, written in an old database language. Our tool asks an AI to rewrite each job for a modern system. Then we check the rewrite by running both on the same data and comparing the results, row by row. The old system's real output is the answer key. The AI doesn't get a vote.

What this review was for. If the answer key decides, the checking has to be airtight. So I went looking for every way the checker could say "matches" when it doesn't. Think of a teacher grading with an answer sheet. Things that would go wrong:

  • Only marking page one of a four-page exam (finding 1). The checker only looked at one of the four tables the job writes.
  • Accepting "3.0" when the answer is "3" (finding 2). The numbers looked the same, but the format was different, and the format matters to whoever uses the table next.
  • Skipping a question entirely because its answer changes daily (finding 3). Some fields are a timestamp of "when the job ran", so they'll never match. But we should still check the student wrote something there.
  • Grading last week's exam by mistake (finding 4). If the new attempt crashed, the old results were still on the desk.
  • Leaving the answer sheet on the desk during the exam (finding 6). The AI's code could open the answer key and copy it. That's the big one, and the fix is to run it in a room that only has the question paper.

And two ways an honest answer could be marked wrong:

  • The marker's clock was set to Irish time (finding 9). One date came out an hour off, only because of the laptop's timezone. On a computer set to UTC it's fine.
  • The answer sheet's boxes were drawn too small (finding 8). We recorded "prices up to 1,899" because that's what we'd seen, so a price of 12,500 didn't fit, even though the old system handles it fine.

How we know it's real. Every finding comes with a small test that shows it happening. 22 tests fail today, one per problem; they'll pass once each is fixed. 37 more pass and protect the parts that already work. One test generates hundreds of random tables, changes one thing, and makes sure the checker notices. It always did. That's the heart of the checker, and it's solid.

The one-line version for the stage: "We didn't just check the AI; we checked the checker, found where it could be fooled, and wrote a test for each one."
