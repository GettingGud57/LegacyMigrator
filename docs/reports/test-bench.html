What's new, most interesting first

1. We tested the tester

I made nine copies of the real Sale translation, each with one realistic mistake an AI could make, and ran each one through the real checker on the dev data and on the holdout data. A checker that says PASS to everything is worthless, so this is the strongest evidence we have that ours isn't. Full table below.

2. "Which columns can never match?" is now answered by evidence

migrator/probe.py stages the input once, then runs the legacy job twice, each time inside a transaction that gets rolled back. Both runs start from identical tables, so any column that comes out different was not decided by the input. It found exactly what we'd guessed by hand for Sale, plus one more for City:

JobTableColumn that differs between two legacy runsWhy (recorded in jobs/evidence/)

A technical judge will ask "how do you know you're not hiding a bug by ignoring a column?". The answer is now a file with example values from both runs.

3. Ignoring a column no longer makes the checker blind to it

Leaving Data Load Completed out of the comparison would let a translation scribble over that column on every row and still pass. So migrator/check.py runs three checks per table, and all of them go through the owner's diff.reconcile:

  1. Whole rows. Every column must match, except that an ignored column is reduced to "filled in or empty". So it must still be filled on exactly the same rows as the legacy output.
  2. Untouched rows. Rows the legacy job didn't change must come out of Spark identical in every column, ignored ones included. Only rows the job really wrote get a pass on their ID number.
  3. Unique key. The Spark output must not repeat a primary key value (SQL Server would refuse such a table).

This paid off right away. Movement's translation passed check 1 on Integration.Lineage. Check 2 caught that it had changed the type of Data Load Completed on all 13 rows the legacy job never touched.

4. Point it at a procedure and it finds the tables itself

The hard-coded JOBS dict is gone. A job is now a small JSON file (jobs/sale.json is four lines). migrator/discover.py asks SQL Server's own dependency metadata (sys.dm_sql_referenced_entities, following any procedures it calls) which tables a procedure touches and which it writes. It reads key columns from primary keys and unique indexes. For Sale it finds the same 8 tables as the old hand-written list:

5. A holdout window picked from the data, not "the previous month"

scripts/holdout_stats.sql replays every sale in the shop through the procedure's dimension lookups, plus four wrong versions of the lookup, and counts per month where the answers would differ. What it showed:

  • Every month already exposes NULL instead of 0 and missing Valid To. The dev window catches those on its own.
  • The numbers looked as if every month from mid-2013 on would also catch a reversed TOP(1). The planted-bug run showed otherwise: every one of those cases is a tie (see below).
  • >= instead of > changes the answer in no month at all, because no sale timestamp ever equals the start of a dimension version. No window of real data can catch that bug.
  • The dev window has 0 sales within 14 days after a city version change. July 2015 has 623, right after 13 states and 18 countries changed on 2015-07-01.
  • The dev window ends exactly at the current ETL cutoff, so the job "updates" the cutoff to the value it already had. A translation that forgets that step looks perfect on dev.

So the holdout is 2015-06-20 to 2015-07-20: 6,143 lines from 1,911 invoices. It lives in jobs/sale_holdout.json, which only changes the staging window.

6. One command to a ready bench

scripts/bench.sh takes a fresh machine to a working bench. It starts Docker, writes a .env with a random password, starts SQL Server and waits until it answers, downloads both backups and checks their SHA-256, restores them, installs ODBC Driver 18, makes the venv from the new pinned requirements.txt, then proves Python can connect. It is safe to rerun. I tested it by deleting the container, its volume, .env, .venv, the ODBC driver and the download cache: it rebuilt everything in 43 seconds (the SQL Server image was already pulled; pulling it took another 27 s).

The MERGE itself is right: all 5,053 updated movement rows match. The failure is one realistic mistake. The code casts timestamps with .cast("timestamp"), which in Spark means "a moment in time, with a time zone". SQL Server's datetime2 has no time zone (Spark calls that timestamp_ntz). The values are the same moment, but the column changed type: 2016-06-06 12:31:17 came back as 2016-06-06 12:31:17+00:00. A downstream report would now apply time zone rules to it, so I count it as a real failure. That's exactly the kind of thing loop.py should feed back. The Sale translation avoided it by casting to the input column's own type.

How to run it on the Mac

From the repo folder, one line at a time. If the bench is already set up, start at step 2.

git fetch origin && git checkout claude/test-bench

1. Set up (safe to rerun; it skips whatever is already done). On the Mac it uses your existing .env and stops with the brew steps if ODBC Driver 18 is missing:

scripts/bench.sh
source .venv/bin/activate

2. Sale, dev data (your existing workflow, unchanged):

python migrator/run_legacy.py sale
python migrator/run_spark.py sale jobs_pyspark/sale.py
python migrator/check.py sale

3. Find the never-matching columns from evidence (writes jobs/evidence/sale.json; already committed for all four jobs):

python migrator/probe.py sale

4. Holdout (same translation, a window it never saw):

python migrator/run_legacy.py sale_holdout
python migrator/run_spark.py sale_holdout jobs_pyspark/sale.py
python migrator/check.py sale_holdout

5. City and Movement (swap the name):

python migrator/run_legacy.py city
python migrator/run_spark.py city jobs_pyspark/city.py
python migrator/check.py city

6. Planted bugs (about 15 minutes, needs step 2 and 4 first), then gather everything into one JSON file:

python scripts/make_planted_bugs.py
python scripts/run_planted_bugs.py
python scripts/collect_results.py

See what a procedure touches, without running anything:

python migrator/discover.py movement

Check your Mac's versions match requirements.txt (pip freeze). PySpark 4 needs Java 17 or 21. If you were on PySpark 3.5, the pin is a change, so rerun sale.py once to confirm it still passes there.

Decisions and why

  • Never ignore a column without evidence. The ignore list comes from probe.py's two runs, not from a guess, and every entry carries a reason and example values. sale.json no longer lists any by hand.
  • Ignored still means checked. Masking to "filled or empty" plus the untouched-rows check means the only freedom a translation gets is the exact value of a column on the rows the legacy job really wrote. Ignoring outright would have passed Movement's Lineage table.
  • All tables, not just the written ones. The read-only dimension tables are compared too. It costs seconds and proves the translation didn't touch them.
  • The verdict stays in diff.reconcile. check.py only chooses which rows and columns to hand it. I didn't edit diff.py, translate.py or create loop.py.
  • Staging window through SQL Server's session context. The staging scripts read SESSION_CONTEXT(N'window_from') and fall back to today's default. This keeps the scripts runnable by hand in any SQL tool, with no text templating.
  • City gets a 2015 window. The default month has zero city changes, so City_Staging would be empty and any translation would pass. A test that can't fail proves nothing.
  • JSON specs with extends. Python 3.10 has no tomllib. sale_holdout.json is just "sale, with another window", so the two can't drift apart.
  • PySpark 4.2.1, Python 3.10, Java 21. 3.10 matches the Mac. PySpark 4 turns on ANSI mode by default, which raises errors on overflow and bad casts the way SQL Server does, instead of quietly returning NULL.
  • Mutants as committed files plus a generator. You can read each planted bug as a normal file, and the generator refuses to run if sale.py changes under it.
  • Backup checksums are pinned by us. Microsoft doesn't publish SHA-256 values for these files, so bench.sh pins the ones from today's download. They catch a broken or swapped download. They don't prove the file is Microsoft's.

What didn't work, the limits, and what's left

  • Three planted bugs got through, and each one teaches something. Reversed TOP(1) can't change a result on a well-formed history: date ranges never overlap, so at most one version is valid at any moment. The only multi-matches (776 dev lookups) are ties with the same Valid From. That points at a real risk: the legacy TOP(1) ORDER BY [Valid From] doesn't say which tied row wins. SQL Server picked the lowest key all 776 times, and the translation matches only because it also breaks ties on the lowest key. A different query plan on the legacy side could flip it. A planted tie-break bug (highest key wins) would be caught on dev, and the probe can't see it because both runs use the same plan. The other two: >= instead of > never changes a result because no sale timestamp equals a dimension version start in this data (measured over all 228,265 sales). A tiny hand-made boundary dataset would catch it: one sale stamped exactly at a Valid From. The decimal-scale bug is invisible because diff.reconcile compares values, and Python treats 15.000 and 15.00 as equal. A schema check (compare column types between after/ and spark/) would catch it, and would also have explained the Movement failure in one line.
  • A staging error I saw twice and couldn't reproduce. Right after adding the window parameter, Sale staging failed twice in a row with SQL Server error 41317 (a transaction touching an in-memory table can't reach a second database). The unmodified script failed the same way, so it wasn't the change. After I emptied Sale_Staging by hand it went away, and 8 more attempts in every order worked. If it shows up on the Mac, empty the table and rerun: DELETE FROM Integration.Sale_Staging.
  • Movement's MERGE only took the "update" branch. Every movement in the window already exists in Fact.Movement, so the "insert" branch never ran. A holdout for Movement should include transactions the warehouse hasn't seen.
  • One guess in the Movement loader. The shop extract returns [Transaction Occurred When] and the staging column is [Last Modifed When] (Microsoft's typo). It's the only date-time column, so the SSIS package must map one onto the other, but I couldn't open the package to confirm.
  • Only Sale has a holdout. City and Movement have dev data only.
  • Each staging load leaves a Lineage row behind (it runs outside the rolled-back transaction, as before). Harmless, but Integration.Lineage grows by one per run or probe. A bench.sh --reset restores the warehouse.
  • "Modified again" invoices don't exist in this data. I looked for invoices edited more than a day after the invoice date and found none, so that case stays untested.
  • The holdout snapshots live inside the repo folder (snapshots/sale_holdout/, gitignored). Nothing sends them to the AI, but see the translate.py suggestion below.
  • Not done: loop.py (owner's), a holdout for City and Movement, the schema check, lineage, and the review app (sibling branch).

Suggestions for the hand-written files

I didn't touch these. Here's what I'd change and why.

translate.py

  • Turn the AI's tools off. It already runs claude in an empty temp folder, which is good. But the temp folder only changes where it starts. Whether it can still read /Users/.../LegacyMigrator/snapshots/ by full path depends on your local permission settings. I tested both here: plain claude -p was blocked by this machine's default permissions, and claude -p --tools "" has no file access at all, whatever the settings. The prompt already contains everything it needs, so the fix is one argument: subprocess.run(["claude", "-p", "--tools", ""], ...).
  • Describe columns in Spark's words. describe_tables prints Arrow types like timestamp[us]. Saying timestamp_ntz (and adding one rule, "cast to the input column's own type") would probably have saved Movement's first attempt.
  • A small typo in the prompt: "froasm the SQL".

diff.py

  • Consider a column-type comparison next to compare_rows. It's the one class of bug the planted-bug test shows it can't see.
  • If you want the "filled or empty" and "untouched rows" ideas inside reconcile itself, they're about 20 lines in check.py (mask and untouched). Moving them over by hand is yours to decide.

loop.py (when you write it)

  • Feed back only snapshots/<dev job>/check.json. Never run check.py sale_holdout inside the loop, only after it has finished.
  • Movement is a ready-made first test case: one clear failure, two tables, and the explanation is in check.json.

Explaining this to the judges

For the teammate. Plain words, no Spark or warehouse knowledge needed.

The one-sentence version

The AI rewrites an old program in a new language, and then we run the old and the new program on the same data and check every single row of output matches. The AI never gets to mark its own homework.

What's an "answer key"?

Before we let the AI near anything, we run the company's old program and save exactly what it produced. That saved output is the answer key. The AI's version gets the same input, and its output is compared to the key, row by row, column by column. Sale has 228,265 rows in its main table. All of them match.

"But some numbers will always be different"

True, and a judge may ask. Two examples:

  • A timestamp saying when the job ran. Run it at 9:00 and again at 9:01 and you get different answers, so no translation could ever match it.
  • A ticket number. The old database hands out the next free number to each new row, like a deli counter, and it never gives a number back. Run the job twice and the second run gets new tickets.

We don't guess which columns are like this. We run the old program twice on identical input and see which columns change by themselves. Only those get a pass, and we still check they're filled in, and that old rows keep their original ticket numbers.

"How do you know the checker actually works?"

We broke the AI's working code on purpose, nine different ways, each a mistake an AI could plausibly make, like picking a customer's old address instead of their current one, or forgetting to delete old copies before adding new ones. Then we asked the checker. It caught 6 of the 9. For the three it missed, we know exactly why and what would catch them, and we say so. One of them turned out to be a bug that can't change the result on real data at all. A tool that tells you where its own blind spots are is easier to trust than one that claims to be perfect.

"Couldn't the AI just learn the test?"

That's what the holdout is for. We keep a second batch of real data, a different month, that the AI never sees: not in its instructions and not in any error message. A translation that only passes the data it practised on would fail here. We picked that month on purpose. It's right after a big change to the company's list of countries and regions, when mistakes in "which version of the customer's address" would show.

What the AI got right, and wrong, on the first try

  • Sale (match every sale to the right customer, product, city and salesperson, then reload the sales table): correct on both batches of data.
  • City (keep a history of each city's details over time): correct first time.
  • Movement (stock moving in and out): the main logic was correct, but it stored two date columns in a slightly different format, with a time zone added. Our checker caught it. That's the point: it would have slipped past a human skimming the output.

The honest limit

"Pass" means the old and new programs agreed on every row of every dataset we tried. It isn't a mathematical proof, which is impossible in general for programs like these. That's why we recommend running both side by side on real data for a while before switching the old one off.

If a technical judge pokes

  • How do you know which tables a job touches? We ask the database. It keeps a record of what every stored procedure reads and writes.
  • Is the database changed by your tests? No. The old job runs inside a transaction that's undone afterwards.
  • Can anyone reproduce this? One command, scripts/bench.sh, builds the whole setup from nothing in under a minute plus downloads.
