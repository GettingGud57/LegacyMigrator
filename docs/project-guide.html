01What to say first

The 30-second version

Say this

Big companies, insurers especially, run thousands of old database jobs every night, and they want to move them to modern platforms like Spark. AI can translate that code quickly, but AI code can run perfectly and still give slightly wrong numbers. LegacyMigrator uses AI to translate each job, and then checks it: we run the old job and the new one on exactly the same data, and compare every row of the output. The AI never grades its own work. The old system's real output is the answer key.

The 3-minute version

Roughly 30 seconds per paragraph. Don't memorise it word for word. Know the six beats and say them your own way.

1. The problem

Companies have old jobs written in SQL Server's language, T-SQL, or in SAS. Every night they copy the day's data into a reporting database and do the sums. Moving to Spark means rewriting all of them, and that's slow, expensive, and risky. One wrong rounding rule and a premium total is off by a few cents on a million policies.

2. Why AI alone isn't enough

AI can do the rewriting, but you can't trust it on its word. We tried a standard translation tool, sqlglot, on 141 statements from Microsoft's sample jobs. It reported 141 out of 141 successes. The output still contained T-SQL that Spark refuses to run. "Success" from the tool didn't mean the code worked. And code that runs can still be wrong.

3. Our idea

So we don't ask the AI whether it got it right. We ask the old system. We take a snapshot of the input tables, run the real legacy job, and save what it produced. That's the answer key. Then we run the AI's PySpark on the identical input and compare the two outputs, whole row by whole row. Pass means every row matches. Anything else is a fail, with a report that points to the exact rows and columns.

4. What we've shown

We set up Microsoft's sample data warehouse and took one of its real loading jobs, the one that loads sales. Claude translated it into PySpark. On the first table we compared, all 5,224 rows and 26 columns matched the legacy output exactly. We're now comparing the job's other output tables and adding two more jobs: one that keeps history, and one that uses MERGE.

5. Why you can trust it

The AI never sees the answer key, only the old code and the table layouts. The part that decides pass or fail is written by hand, not by AI. And we're adding a holdout dataset: data the AI never gets any feedback from, so it can't just tune itself to pass our tests.

6. What it means for EXL

In insurance, a migration isn't done when the code runs. It's done when the numbers match and someone can show they match. This tool turns that check into something automatic and repeatable for every job. A pass isn't a mathematical proof, and we say so. It's strong evidence, and it tells you exactly where to look when there's a problem.

Beat 4 says "now comparing" and "adding". Update it as things land. See Where things stand.

02The problem

Old jobs that run every night

Picture an insurer. Every day, policies are sold, claims come in, payments go out. All of that lands in the company's live systems. Every night, a batch of programs wakes up, copies the day's records into a separate reporting database, and does the sums: total premiums by region, claims paid this month, reserves.

Those programs are called ETL jobs (extract, transform, load). In a lot of companies they were written 10 to 25 years ago, in T-SQL (SQL Server's version of SQL) or SAS (a statistics language that's big in insurance and banking). There can be hundreds or thousands of them. The people who wrote them have often left.

Why companies move them to Spark

  • Data outgrew the box. These jobs usually run on one big database server. When data grows, the only option is a bigger, more expensive server, and there's a ceiling.
  • Spark spreads the work across many machines. Add machines when there's more data. In the cloud, you only pay for them while the job runs.
  • Licences and lock-in. SQL Server and SAS licences are expensive. Spark is free, open-source software, and runs on all the big cloud platforms.
  • One place for everything. Companies want reporting, data science and machine learning on the same data, in the same tools. Spark and Python fit that.

Why AI translation on its own is risky

Rewriting thousands of jobs by hand takes years. AI can write a first draft in seconds. The catch: the dangerous mistake isn't code that crashes. Crashes are easy to spot. The dangerous mistake is code that runs fine and gives slightly different numbers.

Two real examples of how that happens. Both are differences between how SQL Server and Spark behave:

What the code saysSQL Server givesSpark gives
7 / 233.5
'Cork' = 'Cork  'truefalse
SQL Server does whole-number division when both numbers are whole, and ignores trailing spaces when comparing text. Spark does neither. A word-for-word translation runs fine and gives a different answer.

Now picture that inside a premium calculation, applied to a million policies. Nothing crashes. Nobody notices for months. Then the finance team's totals don't match the old reports, and nobody knows which of the 400 migrated jobs is the cause.

Why proof matters in insurance

Insurers are regulated. Their numbers feed financial statements, reserves (money set aside to pay future claims) and reports to regulators. Auditors expect the company to show that a system change didn't change the numbers. "The AI said it was fine" isn't an answer an auditor accepts. "Here's the old output, here's the new output, here's the row-by-row comparison, and they match" is.

That's the gap LegacyMigrator fills.

03The fundamentals, from zero

Each idea here is one you'll need to understand the rest. They build on each other, so go in order the first time.

Database

A database is a program that stores tables and lets you ask questions about them. A table is like a spreadsheet tab with strict rules: every column has a name and a type (whole number, date, text), and every row follows the same layout.

The database we use is SQL Server, Microsoft's database. Inside one SQL Server you can have several databases, and inside each database, tables are grouped into named folders called schemas. That's why our table names have two parts:

Full nameSchema (folder)Table
Fact.SaleFactSale
Dimension.CustomerDimensionCustomer
Integration.Sale_StagingIntegrationSale_Staging

Square brackets, like [Stock Item] or [Customer Key], are how SQL Server lets names contain spaces. Microsoft's sample uses spaces everywhere, so you'll see a lot of brackets.

Careful: "schema" also has a second meaning, a table's layout (its column names and types). People use both. Context tells you which.

SQL vs T-SQL

SQL is the standard language for asking databases questions. Every database speaks it, but each one adds its own extras and quirks. T-SQL ("Transact-SQL") is Microsoft's version for SQL Server. Spark has its own version too, called Spark SQL.

The basics are the same everywhere. The extras are where translation gets hard. Here's T-SQL from the actual Sale job, with the T-SQL-only parts pointed out:

DECLARE @LineageKey int = (SELECT TOP(1) [Lineage Key]   -- variables with @, and TOP(1)
                           FROM Integration.Lineage
                           WHERE [Table Name] = N'Sale'
                           AND [Data Load Completed] IS NULL
                           ORDER BY [Lineage Key] DESC);

DELETE s                                                 -- "DELETE alias FROM": T-SQL only
FROM Fact.Sale AS s
WHERE s.[WWI Invoice ID] IN (SELECT [WWI Invoice ID] FROM Integration.Sale_Staging);

Spark can't run either statement as written. And even where both languages accept the same words, they can mean different things, like the 7 / 2 example above.

Stored procedure

A stored procedure is a named program saved inside the database. Instead of sending SQL from outside, you say EXEC Integration.MigrateStagedSaleData and the database runs the whole thing: several SQL statements in order, with variables, maybe some IF logic. It's like a Python function that lives in the database.

Our three test jobs are stored procedures written by Microsoft. They live in legacy_jobs/wwi/. The Sale one is 84 lines. It returns 0 when it finishes.

The shop vs the warehouse (OLTP vs OLAP)

Think of a café.

The till records every sale the moment it happens: one coffee, one muffin, card payment, 9:14am. It has to be fast and never lose a sale. It doesn't care about monthly trends.

The accountant's spreadsheet is for questions like "how much did we sell on Saturdays in March, compared to last year?" Nobody types into it during service. Once a night, someone copies the till roll into it, tidied up and in one consistent layout.

Companies have the same split, with fancier names:

  • The till is the live system, or OLTP (online transaction processing). Lots of tiny, fast writes. Each fact is stored once, split across many tables (receipts, receipt lines, customers, products), so nothing is ever duplicated or out of date.
  • The spreadsheet is the data warehouse, or OLAP (online analytical processing). Few writes, big read-only questions. Data is laid out flat, one wide row per thing sold, so reports don't have to stitch ten tables together.

The warehouse lives on a separate system, so a big report never slows down the till. And it keeps history the live system throws away. When a customer moves city, the live system overwrites the old address. The warehouse remembers both.

Microsoft's sample, WideWorldImporters, has both halves: a pretend wholesale company with a shop database (WideWorldImporters) and a warehouse database (WideWorldImportersDW, already holding 228,265 sales). Our jobs are the nightly copying jobs between them.

Star schema: fact tables and dimension tables

Warehouses are usually laid out as a star schema. In the middle is a fact table: one row per event, holding the numbers you add up. Around it are dimension tables: the who, where and what, which you use to group and filter.

In WideWorldImporters, Fact.Sale has one row per line on an invoice. Its numbers (called measures) are things like Quantity, Unit Price, Tax Amount, Profit and Total Including Tax. Instead of storing the customer's name and city on every row, it stores a small number, a key, that points at the right row in a dimension table.

Why bother? The customer's details are stored once, not on 228,265 rows. And reports become simple: join the fact table to the dimension you care about, group, and add up.

Keeping history in dimensions (Valid From / Valid To)

Say customer 832 moved from Cork to Dublin in March 2016. A sale from January should still count as a Cork sale. A sale from May is a Dublin sale. If the warehouse simply overwrote the city, every old report would change.

So the warehouse never overwrites. When something changes, it closes the old row and adds a new one. Each row has two dates saying when it was true:

Customer KeyWWI Customer IDCityValid FromValid To
318832Cork2013-01-012016-03-14
433832Dublin2016-03-149999-12-31 23:59:59.9999999
Same customer, two versions. "Valid To = year 9999" means "still true today". Values are illustrative.

This is called a slowly changing dimension, and this exact style (new row per change, with date ranges) is known as Type 2. The City job in our test set is precisely this: it closes off current rows by setting their Valid To, then inserts the new versions.

The important consequence: to find the right Customer Key for a sale, you need the version that was valid at the time of the sale. The Sale job does exactly that lookup, using each sale's Last Modified When time.

Surrogate keys and identity columns

Notice there are two different numbers for the same customer:

  • WWI Customer ID = 832 is the shop's own number for the customer. It never changes. This is called the business key.
  • Customer Key = 318 or 433 is the warehouse's number for one version of the customer. It's called a surrogate key: a made-up number with no meaning except "this row".

Surrogate keys are handed out automatically by the database: insert a row and SQL Server gives it the next number. A column that numbers itself like that is called an identity column. Fact.Sale's Sale Key works this way.

One detail that matters a lot for us: if a transaction that used some of those numbers is undone, SQL Server does not hand the numbers back. The next insert continues after them. Keep that in mind; it comes back in values that can never match.

And there's a special key, 0. When the Sale job can't find a matching dimension row, it fills in 0 rather than leaving the key empty (that's the COALESCE(..., 0) in the code). The warehouse uses 0 to mean "unknown".

Staging tables

A staging table is a waiting area. The live system's data is dropped there first, raw, and then a job processes it into the real warehouse tables. Like a chef who only cooks from the tray on the counter, never straight from the delivery van.

For sales, the tray is Integration.Sale_Staging. When a sale arrives there, it has the shop's numbers (WWI Customer ID, WWI City ID and so on) filled in, but the warehouse's keys are empty, because working those out is the job's work:

Sale Staging KeyWWI Customer IDLast Modified WhenCustomer Key
31078322016-05-20 11:00empty (NULL)
One staging row, before the job. Values are illustrative.

One Microsoft-specific detail: this staging table is memory-only (MEMORY_OPTIMIZED, DURABILITY = SCHEMA_ONLY). SQL Server keeps its layout but never saves its rows to disk, so every restart empties it. That's why our setup reloads it before every run.

ETL jobs

ETL stands for extract, transform, load:

  1. Extract: pull the changed records out of the live system.
  2. Transform: clean them, look things up, reshape them. Here: find the right warehouse key for each customer, city, product and salesperson.
  3. Load: write them into the warehouse tables.

In Microsoft's design, step 1 is done by a separate Windows-only tool called SSIS, which fills the staging table. Steps 2 and 3 are the stored procedure. The stored procedure is the thing we migrate. Because SSIS doesn't run on a Mac, scripts/load_sale_staging.sql does step 1 for us: it asks the shop for one month of sales and drops them on the tray.

Transactions and rollback

A transaction is a group of changes that either all happen or none happen. You start one with BEGIN TRAN. At the end, COMMIT makes the changes permanent, or ROLLBACK undoes all of them as if nothing happened.

The classic example is a bank transfer: take money from account A, add it to account B. If the machine crashes between the two, you want neither to have happened.

We use rollback for something more useful. To get the answer key, we need to really run the legacy job, which really changes the warehouse. So run_legacy.py opens a transaction, takes a "before" photo of every table, runs the job, takes an "after" photo, and rolls back. The database ends up exactly as it started, so we can do it again and again.

Two small details you might get asked about. The Sale job has its own BEGIN TRAN and COMMIT inside it. When that runs inside our outer transaction, its COMMIT doesn't really commit; SQL Server only makes changes permanent when the outermost transaction commits, and ours rolls back. And because staging is loaded outside the undo, the logbook table Integration.Lineage gains one row per run. That's harmless.

Spark, and why one big machine isn't enough

Apache Spark is free software for processing data that's too big for one computer. You write what you want done ("join these tables, filter, add up by region"), and Spark splits the data into chunks called partitions and has many machines work on different chunks at the same time.

A Spark setup has one coordinator, the driver, which plans the work, and many executors (worker processes, usually on separate machines) which do it. A group of machines working together like that is a cluster.

Why not just buy one huge server? Three reasons. Big servers get disproportionately expensive, and there's a largest one you can buy. A cluster grows by adding cheap machines, and in the cloud you rent them only for the hour the job runs. And if one machine in a cluster dies, Spark re-runs just that machine's chunk somewhere else.

Be honest about our setup

We run Spark in local mode (master("local[*]") in run_spark.py): the driver and executors all run on one laptop, using all its cores. That's normal for development. The same PySpark code runs unchanged on a real cluster. For 5,224 rows Spark is overkill, and actually slower than SQL Server because of start-up time. The point is that Spark is where these jobs are moving to.

DataFrames

A DataFrame is Spark's word for a table: rows and named, typed columns. If you know SQL tables and Python lists, you already know most of it.

Python list of dicts 
sales = [
  {"Customer": "Anna", "Quantity": 24},
  {"Customer": "Ben",  "Quantity": 3},
]
big = [s for s in sales
       if s["Quantity"] > 10]
PySpark DataFrame 
sales = spark.read.parquet("sales.parquet")

big = sales.filter(
    F.col("Quantity") > 10
)

Same idea, three differences that matter:

  • It's spread across machines. The rows aren't in one place in memory; each executor holds some partitions.
  • You never change one. There's no "update row 5". Every operation (filter, join, withColumn) gives you a new DataFrame. That's why Spark has no UPDATE or DELETE on these tables, and why translating T-SQL means rebuilding whole tables. A T-SQL DELETE becomes "keep every row except those". A T-SQL UPDATE becomes "make a new table with every row, some with new values".
  • It's lazy. Next section.

In our code you'll see F.col("Customer Key"). F is pyspark.sql.functions, and F.col means "the column called this". It's needed because our column names have spaces.

Lazy evaluation

When you write sales.filter(...), Spark doesn't filter anything. It writes down the step in a plan and hands you back instantly. It only does the work when you ask for an actual result, like counting rows, collecting them into Python, or writing a file. Those are called actions. Everything else is a transformation, which just adds to the plan.

Why? Because once Spark sees the whole plan, it can be smart: skip columns nobody uses, filter before joining instead of after, and avoid moving data between machines more than needed.

The catch is that mistakes show up late. A typo in a column name inside a join may not blow up on that line; it blows up when something finally triggers the work. Our own run_spark.py has a comment about exactly this: "Spark is lazy, so errors in the job's transformations often only surface here", at the step that writes the output files.

PySpark

Spark itself is written in Scala and runs on Java. PySpark is the Python way to use it: you write Python, and PySpark passes your plan to the Spark engine. That's why our setup needs Java installed (JAVA_HOME in .env) even though we only write Python. The challenge asks for the legacy jobs to be migrated to PySpark.

Parquet vs CSV

We save every table snapshot as a Parquet file. Here's why not CSV:

CSVParquet
TypesEverything is text. Is 0012 a number or a code? Is an empty cell NULL or an empty string? You guess.Every column has a stored type: decimal, date, whole number, text.
Exact decimals4.10 often comes back as the float 4.1 or 4.0999999.Stores decimal(18,2) as an exact decimal.

We write the files with pyarrow, a Python library for typed tables, rather than pandas. A specific reason: the warehouse marks current rows with Valid To = year 9999, and pandas' default date type can't go past the year 2262. pyarrow handles it.

One limit worth knowing: SQL Server stores times to 100 nanoseconds (7 decimal places), and Python's datetime stops at microseconds (6). So the snapshots drop the last digit. It would only matter if two timestamps differed by less than a microsecond; the exact match on Sale_Staging suggests it hasn't so far.

Data lakes

A data lake is a big pile of files (usually Parquet) in cheap cloud storage, like Amazon S3 or Azure Data Lake Storage, which engines like Spark read directly. No database server in the middle. When companies move from SQL Server to Spark, their warehouse tables often become folders of Parquet files in a lake.

We don't have a real lake. Our snapshots/ folder plays that role on a laptop: Spark reads Parquet files from it and writes Parquet files back. Swap the folder for cloud storage and the PySpark job doesn't change.

Docker

Docker runs a program inside a sealed box called a container, which carries its own mini operating system. SQL Server is built for Windows and Linux, not macOS, so on the Mac we run Microsoft's official SQL Server container. Our docker-compose.yml describes the box: which image, which port, where the data lives.

The box connects to the outside through a port. 1433:1433 means "port 1433 on the Mac goes to port 1433 in the box", so Python just connects to localhost,1433. The box can't see the Mac's folders, which is why the backup files go in with docker cp.

A Mac-specific gotcha from the devlog: SQL Server's image is built for Intel chips. On an Apple-chip Mac it runs through an emulator, and with Docker's default emulator it crashed after about 8 minutes. Turning on Docker's Rosetta setting fixed it.

What Claude does here, and why its output has to be checked

Claude is a large language model (LLM), made by Anthropic. You give it text, it writes text back. It's trained on huge amounts of text and code, so it's good at writing code that does what a description says.

In our project, migrator/translate.py builds one long message (a prompt) and sends it to Claude through the claude command-line tool. The prompt has three parts:

  1. A set of rules: "write a function run(spark, tables) that returns the changed tables", "Spark has no UPDATE, rebuild the table instead", "match SQL Server's behaviour for NULLs, integer division, decimals and trimming", "only use PySpark, no files, no database connections".
  2. The table layouts: each table's name, its column names and their types. No data.
  3. The legacy stored procedure's code.

Claude replies with one Python code block, which gets saved to jobs_pyspark/sale.py.

Why check it? Because an LLM writes the most likely-looking code, and likely-looking isn't the same as correct. It can miss a rule that the old system applies silently (like whole-number division), break a tie differently, or handle an empty value differently. It does this confidently. It has no way to know it's wrong unless something outside it says so. In our setup, that something is the legacy job's real output.

04How the project works

Four Python scripts in migrator/, run one after another. They don't call each other. They pass files along, through the snapshots/ folder. That makes every step easy to check on its own: you can open any file and see exactly what one step handed to the next.

The four steps, with the real commands

All run from the repo folder. The job name, sale, is how the scripts find the right folder.

  1. Make the answer key. Built

    python migrator/run_legacy.py sale

    Loads staging (by running scripts/load_sale_staging.sql), opens a transaction, saves every table the job touches to snapshots/sale/before/, runs the stored procedure, saves the same tables to snapshots/sale/after/, and rolls back. Also writes snapshots/sale/meta.json with the return code and row counts. The list of tables for each job is written into the script (the JOBS dictionary). Right now it only has sale.

    The Sale job touches 8 tables: Integration.Sale_Staging, Integration.Lineage, Integration.[ETL Cutoff], Dimension.City, Dimension.Customer, Dimension.[Stock Item], Dimension.Employee and Fact.Sale. Every row of every one of them is saved, both times.

  2. Translate. Built

    python migrator/translate.py sale legacy_jobs/wwi/MigrateStagedSaleData.sql

    Reads only the layout of each file in before/ (its column names and types, not its rows), adds the rules and the legacy SQL, and sends it all to Claude using claude -p (the Claude command-line tool in "print" mode: one question in, one answer out). It runs Claude from inside an empty temporary folder, so there are no project files lying around for it to look at. It checks the answer has exactly one Python code block and saves it to jobs_pyspark/sale.py.

  3. Run the translation in Spark. Built

    python migrator/run_spark.py sale jobs_pyspark/sale.py

    Starts Spark on the laptop, loads every file in before/ as a DataFrame, and calls the translation's run(spark, tables) function. It checks the result is a dictionary of known table names to DataFrames, then writes every table to snapshots/sale/spark/: the ones the job returned, plus unchanged copies of the rest. Same file names as after/, so they line up one to one. It prints row counts and how long the job took.

  4. Compare. Built for Sale_Staging; other tables In progress

    python migrator/diff.py

    Right now this runs three fixed comparisons on Integration.Sale_Staging: before vs after (shows what the old job changed), before vs spark, and the one that matters, after vs spark (legacy vs translation). Each prints PASS or FAIL and, on a FAIL, which rows and cells differ. Comparing the other three changed tables, and wiring it up for any job, is the next step.

Every translated job is a Python file with one function:

05One sale line, start to finish

Let's follow one line of one invoice through the whole system. The column names and code are real. The values are made up for illustration, since the snapshots aren't in the repo.

  1. In the shop

    Customer 832 buys 24 bags of "Chocolate frogs 250g" at 4.10 each on invoice 68412. In the shop database this is spread across several tables: the invoice, the invoice line, the customer, the stock item.

  2. Onto the tray

    load_sale_staging.sql calls the shop's Integration.GetSaleUpdates, which flattens those tables into one row per invoice line, and puts each row in Integration.Sale_Staging. In the real run this staged 5,224 lines from 1,604 invoices. Our line looks like this:

    columnvalue
    Sale Staging Key3107
    WWI Invoice ID68412
    DescriptionChocolate frogs 250g
    Quantity / Unit Price / Tax Rate24 / 4.10 / 15.000
    Total Including Tax113.16

    The script also writes a "Sale load started" row into the logbook, Integration.Lineage. In the first run it got Lineage Key 14. The job looks for that open row.

  3. The before photo

    run_legacy.py opens the transaction and saves all 8 tables to before/. Our line is saved with its five key columns empty.

    A small thing with a real effect: every row in before/ has those five columns empty, so pyarrow can't tell what type they are. It stores them with type null. That's why the prompt has a rule saying "a column listed with type null is empty in the input; work out its real type from the SQL".

  4. The old job runs legacy

    For each of the five keys, it finds the dimension row for the right thing, valid at the sale's time. For the customer:

    SET s.[Customer Key] = COALESCE((SELECT TOP(1) c.[Customer Key]
                                   FROM Dimension.Customer AS c
                                   WHERE c.[WWI Customer ID] = s.[WWI Customer ID]
                                   AND s.[Last Modified When] > c.[Valid From]
                                   AND s.[Last Modified When] <= c.[Valid To]
                                   ORDER BY c.[Valid From]), 0)

    In words: "among customer 832's versions, take the one whose date range contains 2016-05-20 11:00. If there's none, use 0." That's version 433 from the history example. Same for city, bill-to customer, stock item and salesperson.

    Then it deletes every Fact.Sale row for invoice 68412 (in case the invoice was loaded before and has changed), inserts our line as a fresh row with Lineage Key 14, marks lineage row 14 as finished with the current time, and moves the "loaded up to" time in Integration.[ETL Cutoff].

    cond = (

06How the comparison works, and why it's trustworthy

This is the heart of the project. If the comparison is weak, nothing else matters. migrator/diff.py is written by hand on purpose, and the project rules say no AI writes it.

The rule: compare whole rows, count duplicates

The function that decides is reconcile(rows_a, rows_b, key_cols, ignore_cols). A is the legacy output, B the translation's. It works like this:

  1. Pick the columns to compare: every column both tables have, minus any on the ignore list.
  2. Turn each row into a tuple of those values, in the same column order on both sides.
  3. Count how many times each exact tuple appears on each side, using Python's Counter.
  4. Anything that appears more times on one side than the other is a mismatch.

PASS only if there are no mismatched rows on either side, and no column exists on one side only. Anything else is FAIL.

In maths terms this compares the two tables as multisets: bags of rows where order doesn't matter but how many copies matters. Two details that make it strict in the right way:

  • Order doesn't matter. Spark doesn't keep rows in any fixed order, and neither does SQL Server without an ORDER BY. Same rows in a different order is a pass.
  • Copies do matter. Imagine two lines on one invoice with the same item, quantity and price. Once the auto-numbered Sale Key is ignored, they're identical rows. If the translation dropped one, a simple "is every row present?" check would still pass. Counting copies catches it.

Here's that exact case, run through the real diff.py with made-up rows:

FAIL
  identical-twin check: 1 rows in A and 0 in B have no identical twin (2 columns compared)
whole rows only in A (1):
  (24, 68412)

Values compare the way Python compares them. Two empty values (NULL, which Python sees as None) count as equal, which is what you want: both sides left it empty, so they agree. Decimals are compared as exact decimals, never as floats.

Key columns: only for explaining a FAIL

A FAIL that just says "17 rows differ" isn't much help. So if you give reconcile key columns (for staging, Sale Staging Key), it also pairs rows up by that key and reports, cell by cell, what changed. Real output from diff.py on made-up rows, where the translation forgot to fill the bill-to key with 0:

FAIL
  identical-twin check: 1 rows in A and 1 in B have no identical twin (5 columns compared)
  details, pairing rows by key:
rows only in A: 0   rows only in B: 0   rows changed: 1   cells changed: 1
first 1 changes:
  (3107,)  Bill To Customer Key  0 -> None

Read it as: "the row with Sale Staging Key 3107 exists on both sides, and one cell differs: Bill To Customer Key is 0 in legacy and empty in Spark."

The key never decides PASS or FAIL. Why keep it out of the decision? Because keys can lie. A key might not be unique (two rows share it), or it might be one of the columns that can never match. If the verdict depended on pairing by key, a bad key could hide a problem. The whole-row count has no such weak spot. If keys do repeat, the report warns about it and leaves those rows out of the cell-by-cell explanation rather than guessing.

Values that can never match

Some columns will differ between any two runs, even of the same job. Comparing them would always FAIL and tell you nothing. They go on an ignore list for that job. The devlog names three kinds:

KindExample in the Sale jobWhy it can't match
Clock timesIntegration.Lineage
[Data Load Completed]		The job writes SYSDATETIME(), the time right now. Spark writes its own "now", which is a different moment.
Identity keysFact.Sale
[Sale Key]		SQL Server numbers new rows itself. Numbers used inside a rolled-back transaction aren't handed back, so every run of run_legacy.py pushes the counter on by about 5,224, and the order rows get numbered in isn't guaranteed either. The translation can't know the server's counter.
Lineage keysIntegration.Lineage
(new rows per run)		Each staging load opens a new logbook row, and it isn't rolled back. Inside one run both sides read the same before/, so this one is fine within a run; it matters when comparing across runs.

Ignoring a column is a decision a human makes and writes down, per job. It's a short list, and every ignored column is named. The rest of the row is still compared in full, and the row count is still checked, because every row still has to find its twin. For Sale_Staging the ignore list is empty: all 26 columns were compared.

The per-job ignore lists are Planned. reconcile already takes an ignore_cols argument.

Checks on the checker

How do you know the comparison isn't just saying PASS to everything? Two built-in controls:

  • before vs after must FAIL, because the old job really changed the staging table (it filled in five key columns). If this passed, the checker would be broken. It's the first comparison diff.py prints.
  • The no-op job. jobs_pyspark/noop.py changes nothing. Run it through run_spark.py and its output must equal before/ exactly. When it does, that shows the Spark round trip itself (reading Parquet, writing Parquet, timestamps, decimals) doesn't alter data. So when a real translation fails, the fault is in the translation, not the plumbing.

A third control is In progress on the test-bench branch: planted bugs. Take a correct translation, break it on purpose in a small way (wrong rounding, a dropped NULL check), and make sure the comparison catches each one.

Dev data and holdout data

Once the retry loop exists, the AI will see the FAIL reports and try again. That creates a risk: it could learn to pass our data rather than learn the job. For example by special-casing one invoice that kept failing.

The fix is the same one used in machine learning and in exams: keep some questions back.

  • The dev dataset is what the loop runs on. The AI gets the mismatches and can fix against them.
  • The holdout dataset is different data (for example, a different time window, with different customers and edge cases) that the AI never gets any feedback from. Not the data, not the mismatches, not even whether it passed. Only the final check runs on it, and the result goes to people.

A translation that really understood the job passes both. One that was tuned to the dev data tends to fail the holdout. The project rules say it plainly: "The translator must never see holdout data or holdout diffs." In progress on the test-bench branch.

"The AI never grades its own work"

This is the one-line summary of everything above, and you should be able to back it up with three facts:

  1. The answer key comes from the old system, not from the AI. It's the real output of the real legacy job, saved before the AI is involved.
  2. The AI never sees the answer key. Its prompt has the old code and the table layouts, and nothing else. You can show this: it's all in build_prompt in migrator/translate.py.
  3. The judge is hand-written. diff.py isn't AI-written, by project rule. So the AI can't write a translation and a lenient test that agree with each other.

Why does this matter? If you ask an AI to write code and then also write the tests for it, both come from the same understanding. If it misunderstood the job, the tests will share the misunderstanding and pass. Using the legacy system as the referee breaks that circle.

What a pass does and doesn't prove

Be precise here. It's where a sharp judge will push, and it's where being honest makes you look stronger.

A pass proves: on this input data, the translation produced exactly the same tables as the legacy job, every row and every compared column.

A pass doesn't prove: that the two programs agree on every possible input. A concrete example: the Sale job fills a key with 0 when no matching dimension row exists. If none of our test sales happens to have a missing match, a translation that forgot that rule would still pass. It would only fail on the day such a sale arrives.

Could you prove it properly instead? In general, no. Computer scientists showed long ago that no program can decide, for every pair of SQL queries, whether they always give the same result. The problem is undecidable. There are tools that can prove it for limited kinds of queries, but not for real stored procedures with variables, updates and ordering.

So the honest position, and it's in our Responsible AI note:

Say this

A pass means the old and new job agreed on every dataset we tested, including one the AI never saw. That's strong evidence, not a mathematical proof. Before a real company switches off a legacy job, they should run old and new side by side on real production data for a while, and our tool is exactly what you'd use to compare them each night.

That side-by-side period is called a parallel run. It's standard practice in banking and insurance migrations already. Our tool makes it cheap and automatic.

The ways to make "on this data" cover more cases are: more datasets, a holdout the AI hasn't seen, and data picked to include edge cases (NULLs, ties, missing matches, history changes). The test bench work is aimed at exactly that.
